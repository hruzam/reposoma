## The useful minimum: four moves

The same preparation method applies to a Terra- or Sol-carried myShell. Model/effort does
not change its authority. Select deeper help for a concrete unresolved question.

1. **Resolve the outcome and owner.** Read local instructions and the operator's current
   request. Identify the named project/bed, intended output, existing authorization and
   actual owner. Use project-saddle's controller plus selected saddle-project function to
   verify the project frame and read order. That procedure is read-only. Check whether the
   request belongs to an existing gate before proposing a new session. A cold start alone
   does not open another bed or make myShell a project head.
2. **Recover evidence relevant to the first assignment.** Start with current owner STATUS,
   the relevant RUNBOOK, Majkee's words and named inherited sources. Follow targeted journal
   pointers and later receipts. Expand reading only when a gap can change scope, ownership,
   acceptance or the first useful action. Do not reload the whole history, all skills or the
   full roster by default. Check likely evidence homes before inheriting a negative claim.
3. **Prepare the smallest usable handoff.** For a small task, a bounded assignment can be
   enough. Where a RUNBOOK is requested/earned, use one gate, one status owner, an exact
   first assignment, owned paths, acceptance evidence, dependencies and a recovery probe.
   Author project surfaces only under the separately established task authority, in the
   project's declared session root. A journal procedure grants no project pen. Later work
   can have unresolved dependencies; the first assignment cannot be called executable
   while its own prerequisites remain unmet.
4. **Check and hand off.** Check the actual selected role contracts, source pointers,
   YAML/meaningful command formatting, RUNBOOK/STATUS gate agreement and the first action.
   Use fresh review where the project contract or consequential scope requires it. Return
   exact paths, next seat, first action and any concrete blocker. Preparation ends when
   that action is executable and required checks pass, or when a named dependency needs
   its owner's decision. Record a receipt when authorized; do not keep designing helpers
   merely because another possible improvement is visible.

These are four moves, not four additional gates. Oraculum's fuller seven-step explanation
helps reasoning; Astrobley's compressed version is the usable routine. Fixed 20/45-minute
deadlines were unmeasured suggestions and are not adopted. Explain a material preparation
delay by its actual missing input rather than inventing a time-based waiver of required reads.

## Reusable RUNBOOK section: Communication

Copy and adapt this paragraph to the actual participants; it creates no automatic route:

> Each head owns its bed, integration and STATUS. Address the intended person/session in
> ordinary language, naming the bounded ask, needed sources and expected result; refer to
> the existing assignment authority where needed. Use native routing for an available
> authorized child, and Majkee's relay or an explicitly authorized checked route between
> separate CLI heads. Record an observed handle/session binding when it becomes available;
> an idle child can still be addressable. Preparation is not delivery, acknowledgement is
> not acceptance, and file presence proves neither. If the recipient is unavailable, retain
> the ask and return the exact reconnection action to its owner. A header authorizes no
> sending, spawning or transport. Keep exact syntax only where an actual card, binder or
> file contract requires it; existing _bus artifacts retain their own GUIDE format.

Sender identity need not be repeated when the native route already makes it unambiguous.
Qualify names when needed, e.g. Claude Oraculum / X3 head versus Codex Oraculum / consult.
Record the actual instance, owning bed and last binding check in the existing assignment or
owner record, not another registry. An unstarted roster has no invented live handles. A new
incarnation does not inherit an old handle merely because its name matches.

to-/from- markers can remain useful for human-held relays, but are optional presentation.
Preserve mandatory card selection, formal file fields, and explicitly required verbatim
relay. Do not infer read/acceptance/completion from a tool receipt or repeat this paragraph
as a checklist on every message. Record delivery distinctions only when useful to the task.

## Where our process is becoming too expensive

Ownership, actual source checks, recovery and required independent acceptance address real
failures. Some of our preparation is nevertheless overengineered when the following become
defaults: a 43-role survey; a panel for routine wording; every historical journal; a new card
beside every launcher; a gavel formatter, inbox script or transport build before the first
project assignment. Keep X3's unusual first-route proof and publication checks scoped to X3.
They are not the template for a routine component task.

Do not remove a current required check on the strength of this opinion. Reduce future
ceremony by task consequence, and propose a scoped change if an existing gate needs revision.
The practical test is whether a surface removes repeated work or a demonstrated failure.
If it only creates another surface to reconcile, defer it and let the project proceed.

The X2 Houston consult write request found during this review is a concrete example: a
launcher can be elaborate and still contradict the chosen role. Correct the assignment to
a text-only return, with the head preserving attribution; do not widen Houston's card.
