# session-coordination

Coordinate several explicitly selected sessions through a retained team per session.
The coordinator holds the cross-session overview; each team absorbs its session detail.
A process is one selected function invocation. This is a manual local whole line,
not an installed global program, event listener, parser or production dispatcher.

## Invariants

- Adopting this procedure does not resume a coordination frame. Select sessions from
  the current assignment or an explicitly authorized continuation. Examples, historical
  receipts and another coordinator's cold-start card do not implicitly select sessions.
- Each owning session retains its head, gate, integration and sole doing-state.
  A support team never becomes a second project head. No shared project STATUS.
- A session team has distinct context-liaison, input-preprocessor, strategic-thinker
  and development-adviser slots; factual research is optional. Retain separate
  session-bound instances where useful. They are not one global specialist pool.
  The caller supplies native bindings; no slot grants tools, authority or delegation.
- All team dispatch/integration stays with the coordinator. Members may recommend
  another member's involvement; they cannot dispatch or escalate themselves.
- Attachment does not mean continuous execution. Reuse available instances; activate
  only the members needed by the event. An uncreated slot is planned, not briefed.
  Bound, prepared and active are different observations. A role name restores no context.
- Separate operator words, source facts, interpretation and proposals. Refresh facts
  changed by an event. Verify consequential claims against sources; summaries can be stale.
- Store current bindings and dated readiness in an existing authorized coordination
  receipt or runtime context, not this program. Project next actions remain with their
  owners. Record no transcript dump, credentials or private history.
- Bind each member to its coordinator, session and role. Reuse requires that binding
  or an explicitly authorized transfer/continuation; a matching name or native
  addressability alone does not establish it.
- This procedure requires capabilities and grants none. Source reads and native member
  creation/continuation require caller authority and applicable instructions. Default
  team intake is read-only; separately authorized writing requires a suitable native role
  and disjoint paths. No inferred send, commit, deploy, project launch or foreign pen.
- Preserve original request and source identities through the team. File presence,
  assignment, delivery, reported reading and acceptance are not interchangeable.
  Return ambiguity to its owner; do not replace it with an invented decision.

## Required inputs and capabilities

Inputs: selected function; current coordinator/continuation context; original task/event;
explicit project/session paths; applicable instruction/owner-state pointers; supplied
native role bindings and observed handles if
known; allowed effects; desired return; source revision/time where relevant. Missing
selection/authority holds only the affected operation; do not attach a project from cwd.

Capabilities: inspect named sources and owner state; discover/continue authorized native
members; create replacements only when authorized; return attributed evidence. Tools,
models, role contracts and runtime limits are supplied/checked by the caller.
The program does not resolve or modify a vendor harness or depend on a private entry card.

## Team roles and context boundary

| role | retained session responsibility | typical event contribution |
|---|---|---|
| context-liaison | session map, source locations, open dependency pointers | relates the new input to current session evidence |
| input-preprocessor | incoming material and extraction context | separates asks/quotes, removes irrelevant bulk without losing disagreement |
| strategic-thinker | session-specific assumptions and alternatives | bounded deep challenge or consequential framing |
| development-adviser | session-specific practical feasibility and design context | implementation consequences, critique and concrete alternatives |
| factual-researcher | one declared evidence gap | primary-source verification, clearly separated from inference |

The liaison does not own all raw content or summon the team. The coordinator receives
member returns, chooses the needed next member and owns cross-session synthesis. A member
can receive another's bounded result rather than the entire conversation. Sequence steps
when an earlier result can change the next brief. Independent source reads may overlap.
