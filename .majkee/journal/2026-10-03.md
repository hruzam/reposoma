## 1.1 file shape + where it belongs

Codex discovers one standalone TOML per custom agent. Required: `name`, `description`,
`developer_instructions`. The identifier comes from `name`; matching the filename is a convention.
Personal agents live in `~/.codex/agents/`; project agents in `<project>/.codex/agents/`.
[Official file schema](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agent-file-schema).

Minimal illustration — `my_agent` is a placeholder, not an installed agent:

```toml
name = "my_agent"
description = "Use for scoped implementation tasks, bug fixes, and refactoring."
model = "gpt-5.6-terra"
model_reasoning_effort = "high"

developer_instructions = """
Implement the task delegated by the main agent.
Respect the assigned file scope and preserve other work.
Run relevant checks and report changes, results, and remaining issues.
"""
```

Terra's model ID is `gpt-5.6-terra`; `high` is supported.
[Model documentation](https://developers.openai.com/api/docs/models/gpt-5.6-terra).

`description` guides selection; `developer_instructions` governs the child. Explicit model
and effort in the custom file take precedence over inherited/spawn defaults. Set both to pin
Terra/high. Current releases enable subagents by default.
[Configuration semantics](https://learn.chatgpt.com/docs/agent-configuration/subagents#custom-agents).

Local homes, per [codex/README.md](/home/hruzam/ia-sync/codex/README.md) and
[.germline/README.md](/home/hruzam/reposoma/.germline/README.md):

| Surface | Home / rule |
|---|---|
| Portable native Codex files | `~/ia-sync/codex/agents/<name>.toml` → deploy → `~/.codex/agents/<name>.toml` |
| Shared identity, when germline-backed | `~/reposoma/.germline/agents/<slug>/identity.md` → stamped runtime rendering on the ia-sync table |
| A stamped rendering | Edit its source and re-render; do not hand-edit the rendering |
| `~/.germline` | Host-local symlink to the shared source; never a deploy target |

Existing global roles are reused with project guidance; this example does not propose another
global role or a same-name project copy. A new primitive needs the repository's deploy dry run
and fresh-session behavior proof before being called live.

## 1.2 exact caller — correction to the first answer

The first answer gave ordinary-language prompts and missed the tool-level selector.
**In the inspected runtime, the selector is `agent_type`.**

| Field | Job |
|---|---|
| `name` in the agent TOML | Defines the selectable custom agent |
| `agent_type` in `spawn_agent` | Selects that definition |
| `task_name` in this session's spawn interface | Labels the delegated task; does not select the role |
| `message` | Gives the child its actual work, scope, and constraints |

Copyable prompt to the main agent:

```text
Call spawn_agent with agent_type="implementer".
Task: <your task, allowed files, constraints, acceptance criteria>
Wait for its result, then verify and summarize it.
If implementer is unavailable, report that instead of substituting another agent.
```

Corresponding tool arguments in this session:

```json
{
  "agent_type": "implementer",
  "task_name": "implement_fix",
  "message": "Implement <task> within <file scope>. Run relevant checks and report results."
}
```

This selects the existing `implementer` definition, already pinned to Terra/high. The JSON
describes the main agent's tool call; pasting JSON into chat is a request, not direct execution.

Evidence distinction: the active tool schema exposes `agent_type`, `task_name`, and `message`.
Read-only inspection of the installed 0.159.3 binary found `agent_type` and the error text
`unknown agent_type`; zero literal occurrences of `subagent_name` or `subagent_type`.
That binary observation supports this version's finding, not a claim about every interface.
The public docs identify agents by TOML `name` and use `agent_type` in lifecycle events;
they are not the source of the full session-specific JSON above.
