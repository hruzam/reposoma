***Case study — two native entry shapes, one runtime vocabulary***

The distinction is not `profile = identity` versus `agent = settings`. Both TOML shapes can
carry runtime settings; they address different **session origins**.

| artifact | selects / creates | model + effort apply to | instruction role | Houston / Astrobley case |
| --- | --- | --- | --- | --- |
| `~/.codex/houston.config.toml` | a fresh **main** session through `codex --profile houston -C <project>` | that directly launched Houston session | composed Houston render as session `developer_instructions` | planned Houston main-entry artifact; absent on office at Cartan check 2026-10-09 |
| `.codex/agents/houston.toml` | a named **child** when an authorized parent selects/spawns `houston` | that child only, if declared there | same rendered identity, bounded to child cards | project-local candidate; it presently has no `model` or effort, so these inherit |

| `<project>/.codex/config.toml` | no identity — trusted-project layer | eligible settings in that project | project runtime defaults | may refine direct or child runtime, subject to protected-key rules |

**Answer — symlink the profile path, not the TOML schema**

Use a real filesystem symlink at the path Codex already resolves:

```text

  -> /durable/path/houston.profile.config.toml
```

A literal `@/path/to/file` or `@<address-to>houston.config.toml` inside a TOML file is not
TOML include syntax and is not a documented Codex include mechanism.

**Keep profile and custom-agent artifacts separate**

The symlink target must be **profile-shaped**: settings for the directly launched main
session (`model`, `model_reasoning_effort`, approval/sandbox/MCP settings as applicable) plus
the accepted composed Houston `developer_instructions`. Do not point it at
`<project>/.codex/agents/houston.toml`. That file is a custom-agent artifact for a spawned
Houston child and may contain agent-only keys such as `name` and `description`; sharing one
TOML between these two schemas is not a stable contract and can fail strict configuration
validation.

```text
canonical Houston sources
  -> compose / render -> /durable/path/houston.profile.config.toml
  -> symlink          -> ~/.codex/houston.config.toml

project child route
  -> <project>/.codex/agents/houston.toml
```

**Evidence boundary**

Official profile documentation defines the selected path and layering, but does not itself
promise symlink semantics. Support for a symlinked profile is therefore grounded in ordinary
filesystem resolution plus current Codex loader behavior and the configuration-symlink fix
in [openai/codex#9445](https://github.com/openai/codex/pull/9445). That is strong evidence for
the direct profile path, not a guarantee for every discovery mechanism or future release.

Symlink discovery under `agents/*.toml` is a separate path and has had contrary community
evidence, including [openai/codex#15345](https://github.com/openai/codex/issues/15345). Keep
the project custom-agent file ordinary unless that exact route is independently tested on
the installed Codex version.

**Operational cautions**

- Prefer an absolute symlink target and avoid link cycles.
- Run strict-config validation or a cold-start smoke check after installing the link.
- Remember write-through behavior: a tool that rewrites the selected profile may modify the
  symlink target, so treat that target as the owned durable artifact.

a main session or a child. Codex still needs two native TOML artifacts because the entry
schemas differ, but those artifacts do not need to be two maintenance authorities. Maintain
the canonical Houston source set once (identity + Nablarva addendum + Codex binding), compose
it once, and render that same body into both adapters:

```text
canonical Houston source set
  -> one composed developer-instructions body
       -> profile adapter: developer_instructions + main-session settings
       -> child adapter:   name + description + the same developer_instructions
```

The current candidates already exhibit this split: after the child-only `name` and
`description` lines, `.codex/agents/houston.toml` and
`raw/houston.config.toml.candidate` are byte-identical. Therefore the repeated body is a
generated render, not content to hand-maintain in two places. A composition check should fail
if either adapter's body drifts from the canonical inputs or from the other adapter.

**What the symlink does and does not deduplicate**

The profile symlink gives the generated **profile adapter** a durable home and a stable Codex
lookup path. It cannot share only the `developer_instructions` value with the child TOML:
TOML has no native include for a substring, and Codex documents no instruction-file reference
for that field. Whole-file symlinking both routes to one TOML would erase the necessary schema
separation. The practical invariant is therefore one source/composition plus two thin generated
artifacts, not one physical TOML file.

Route-specific settings remain outside the identity invariant. The profile may choose the
main-session model, effort and permissions; the child adapter may set or inherit child-runtime
values. Both must carry the same Houston meaning and cards, while effective permissions remain
bounded by their respective runtime route.

**Invocation authority is a separate boundary**

Making the child adapter discoverable does not authorize every implementer to call Houston.
Nablarva's current L16 contract and composed identity allow `consult` from the session head or
majkee and explicitly route a worker's finding back to the head. If direct worker invocation is
intended, that is an authority change requiring the project's architectural/gavel path; neither
a symlink nor duplicated identity text can make it implicitly.

**Houston profile versus Cartan `AGENTS.md`**

They are not one override stack. A selected profile's `developer_instructions` is injected as a
developer-role message; the global and project `AGENTS.md` chain is discovered separately and
injected afterward as a user-role message. On installed Codex 0.162.0, `codex debug prompt-input`
shows exactly that shape. Therefore a conflicting Cartan identity in `AGENTS.md` does not
technically beat Houston's profile instructions: developer-role Houston has the higher prompt
priority. Compatible repository rules and project facts from `AGENTS.md` still apply.

That technical priority does not grant Houston epistemic authority to overwrite Nablarva canon.
If the Houston profile contradicts project locks or its card, the profile is wrongly composed;
the conflict is curvature to repair, not permission to ignore the project. And because both
identity texts remain model-visible, even a technically resolved Cartan/Houston conflict is
avoidable identity noise.

**Cartan as the no-profile default**

Current Codex has no supported default named-profile selector. Since Codex 0.134.0, top-level
`profile = "cartan"` is no longer supported, so `~/.codex/cartan.config.toml` is inert unless the
launch explicitly uses `--profile cartan`. The native no-flag default is
`~/.codex/config.toml`.

A clean scalar overlay can therefore be:

```text
~/.codex/config.toml
  developer_instructions = <Cartan main-session identity>
  model / effort / ordinary defaults = <Cartan defaults>

~/.codex/houston.config.toml
  developer_instructions = <Houston composed identity>
  only Houston-specific runtime differences
```

With no `--profile`, the base Cartan values apply. With `--profile houston`, the profile layer
overrides the same scalar base keys, including `developer_instructions`. This does not suppress
`AGENTS.md`: global and project instruction discovery still runs for both sessions.

Therefore the clean-switch design would keep role-neutral working agreements and project canon
in `AGENTS.md`, while putting the replaceable main-session identity in base/profile
`developer_instructions`. The current global and Nablarva `AGENTS.md` files both name Cartan, so
adopting that design is a harness/canon change to review, not something the Houston profile or a
symlink should silently repair. If a separate physical `cartan.config.toml` is desired, it can
only become the no-flag base by being the complete target of `~/.codex/config.toml` (for example,
via a filesystem symlink); Codex would then treat it as the base config, not as a selected profile,
and all host-local base settings would need to be preserved.

[Profiles](https://learn.chatgpt.com/docs/config-file/config-advanced#profiles), and
[`AGENTS.md` discovery](https://learn.chatgpt.com/docs/agent-configuration/agents-md).
