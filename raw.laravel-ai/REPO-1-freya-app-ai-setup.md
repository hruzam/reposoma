# Repo 1 — Freya App (project code): AI / Boost Setup Blueprint

Scope: the Laravel 11 application repo only. Everything here is *consumed* at coding
time by Claude Code / Cursor. Authoring of guidelines, agents and research lives in
Repo 2 and is synced here.

---

## 1. Directory layout (AI-relevant parts)

```
freya/
├── .ai/
│   └── guidelines/              # SOURCE of project guidelines (synced from Repo 2)
│       ├── 00-architecture.md   # modular monolith, layer ownership, boundaries
│       ├── 10-php-laravel.md    # coding rules (Povilas-style, trimmed)
│       ├── 20-filament.md       # Filament v4/v5 rules for admin migration
│       └── 30-freya-domain.md   # webshop invariants: orders, stock, pricing
├── .claude/
│   ├── settings.json            # MCP on/off policy, permissions
│   └── skills/                  # on-demand knowledge (NOT loaded upfront)
│       ├── scope-manifests/     # cutting-agent output: per-feature manifests
│       └── opencart-migration/  # strangler-fig playbook, loaded only when needed
├── .mcp.json                    # generated by boost:install (laravel-boost server)
├── CLAUDE.md                    # GENERATED — never edit by hand
├── AGENTS.md                    # generated (Cursor/Codex read this)
└── composer.json
```

Rule of thumb for what goes where:

| Knowledge type                          | Mechanism            | Context cost            |
|-----------------------------------------|----------------------|-------------------------|
| Always-true conventions (small!)        | `.ai/guidelines/*`   | paid every session      |
| Stable but situational (manifests, migration playbooks, package internals) | skills | paid only when activated |
| Live state (schema, routes, logs, data) | Boost MCP tools      | paid per call           |

This mirrors your own structural/semantic split: deterministic + stable → static
artifacts; live + dynamic → MCP.

## 2. Boost lifecycle commands

```bash
# initial / after guideline changes in .ai/guidelines
php artisan boost:install

# refresh published guidelines+skills to match installed package versions
php artisan boost:update

# scan for NEWLY installed packages and offer their guidelines/skills
php artisan boost:update --discover
```

Automate in `composer.json` so the whole team (and every agent run) stays current:

```json
{
  "scripts": {
    "post-update-cmd": [
      "@php artisan boost:update --ansi"
    ]
  }
}
```

Verify the MCP server inside a Claude Code session with `/mcp`. Manual
registration if ever needed:

```bash
claude mcp add -s local -t stdio laravel-boost php artisan boost:mcp
```

## 3. Injecting YOUR OWN composer packages into Boost

This is first-party supported. Boost discovers guidelines from any package in
`vendor/` — including your private/internal ones (path repos, private Packagist,
VCS repos — irrelevant to Boost, it just reads vendor/).

In each of your packages:

```
your-vendor/freya-pricing/
└── resources/
    └── boost/
        ├── guidelines/
        │   └── core.blade.php    # ONE file — Boost reads ONLY this per package
        └── skills/
            └── pricing-rules/    # optional on-demand skills shipped by the package
                └── SKILL.md
```

Behavior:
- When any consuming app runs `php artisan boost:install` (or
  `boost:update --discover` after installing the package), the rendered
  `core.blade.php` is appended into that app's CLAUDE.md / AGENTS.md.
- Boost reads exactly one `core.blade.php` per package. If it grows, split into
  Blade partials and `@include` them from core — Boost still concatenates the
  rendered result into one block.
- It is a Blade file: you can branch on detected versions/config, e.g. emit
  different rules per major version of your own package.

Content discipline for core.blade.php (anti-dilution):
- short "what this package is" (2–3 lines)
- non-obvious conventions only — things an agent cannot infer from reading code
- the 3–5 gotchas that have actually burned someone
- push everything verbose (full API walkthroughs, examples) into shipped *skills*
  instead, so it loads on demand

Overriding Boost's own guidelines also works the same way: a file at
`.ai/guidelines/<package>/<version>/<topic>.blade.php` replaces Boost's default
for that topic.

## 4. Context-budget policy (the Q1 answer, operationalized)

Per-session checklist (cheap, pays for itself):

1. `/context` (or `/cost`) at session start — know your baseline.
2. `/mcp` — disable servers irrelevant to today's task. Boost MCP **off** for
   pure refactors/doc work where guidelines suffice; **on** when you need
   `database-schema`, `tinker`, log reading, or `search-docs`.
3. Guidelines budget: keep the *sum* of `.ai/guidelines/*` under ~300 lines.
   Anything you're tempted to add → ask "is this needed in EVERY session?"
   If no → it's a skill or a manifest.
4. Re-audit quarterly: delete rules the models no longer violate (Povilas cut
   his file in Jan 2026 for exactly this reason).

`.claude/settings.json` sketch for per-repo MCP policy:

```json
{
  "enabledMcpjsonServers": ["laravel-boost"],
  "permissions": {
    "deny": ["Bash(rm -rf *)"]
  }
}
```

(Adjust to taste — the point is the policy lives in the repo, not in heads.)

## 5. Guideline seed — 00-architecture.md (starting point)

```markdown
# Freya Architecture (binding)

- Modular monolith. Two thin presentation layers (storefront, admin/Filament)
  over ONE shared domain core and ONE database. Do not propose service or
  database splits.
- Layer ownership is defined in scope manifests (see skill: scope-manifests).
  Before modifying code in a scope you have not read this session, activate
  its manifest skill instead of rescanning the codebase.
- Slicing terminology: "feature scope" = vertical slice (one domain concept
  across controllers/models/blades/resources); "abstraction level" =
  horizontal layer (abstract → concrete). Use ONLY these definitions.
- Legacy OpenCart admin is being strangled into Filament. New admin features:
  Filament only. Never extend OpenCart code; wrap or replace.
- Dependency direction: presentation → domain core. Domain core never imports
  from storefront/ or admin/. Deptrac enforces this in CI; if your change
  would violate a Deptrac layer rule, stop and flag it instead of working
  around it.
```
